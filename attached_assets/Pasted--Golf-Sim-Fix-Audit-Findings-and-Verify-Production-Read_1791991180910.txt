## Phase 1 — Fix Critical Issues (P0)

### 1. Secure the legacy batch booking endpoint

Investigate `POST /api/book/batch` and determine whether any active application functionality still depends on it.

If unused, safely disable it and add regression tests confirming it cannot create reservations.

If still required, update it to enforce all current booking rules, including closures, cutoff dates, bay availability, valid booking intervals, and conflict detection.

Do not leave a publicly accessible endpoint capable of bypassing booking restrictions.

### 2. Fix reservation overlap detection

Replace any incomplete overlap detection with proper time interval comparisons.

Two reservations overlap when:

`newStart < existingEnd && newEnd > existingStart`

Use the appropriate validated time representations and enforce the application's booking interval rules.

Add automated tests for:
- Exact adjacent reservations.
- Partially overlapping reservations.
- Completely overlapping reservations.
- Off-grid start times.
- Concurrent reservation attempts.
- Closure conflicts.

### 3. Remove customer information from public availability responses

Inspect all public availability endpoints.

Remove customer names, email addresses, phone numbers, and any other unnecessary personal information from their responses.

The public booking system should receive only the information required to display available and unavailable time slots.

Preserve the information needed by authenticated admin interfaces.
